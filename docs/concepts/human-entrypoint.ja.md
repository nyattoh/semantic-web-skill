# Semantic Web Skillを人が使う入口 — 構想のみ

状態: **proposal only / 未実装**。この文書は別ブランチへ保存する構想の作業用草案。アプリ、SaaS、公開サービス、インストーラー、課金、対応OSを実装・確約していない。

## 推奨する順番

1. 現行Skillの具体例・短い使い方・意味判断と実検証の対応を改善する。
2. その手順を再利用する、小さなローカル中心のデスクトップ入口を検討する。
3. チーム共有への実需要が確認できた段階でSaaSを検討する。

この順序は実測した優劣ではなく、既存Skillを優先し、利用者のHTMLやカンプを初期状態で外部へ送らずに利用できる導線を作る提案。デスクトップアプリがブラウザやSaaSより常に低コスト・安全・簡単という主張ではない。

## 共通する利用体験

1. **目的を選ぶ**: カンプからHTML／ブリーフからカンプ／既存HTMLのレビュー。
2. **素材を選ぶ**: ファイル、文章、必要なコンテンツ、対象言語、利用環境。画像だけでは操作の目的が分からないことを明示する。
3. **意味を確認する**: 「これは移動か操作か」「同じ種類の項目か独立した領域か」「入力後に何が起こるか」を、結果を左右する箇所だけ尋ねる。
4. **提案を見る**: カンプ／HTML／意味の対応表と、変更する箇所の差分。既存ファイルを勝手に置換しない。
5. **確認・保存**: 実行した検査、未実施、意味判断、人の確認が必要な項目を分け、成果物・元の入力・手順を保存する。数字の品質点数を出さない。

ボタン名は「意味を整理」「HTML案を作る」「確認を記録」「保存」など、実際にすることに合わせる。結果を得る前に「アクセシビリティ合格」「完全に正しいHTML」「公開可能」と表示しない。利用者向けの一画面目にモデルルーティングや内部の実装詳細を並べない。

## デスクトップ案

- まずHTML/ブリーフと作業フォルダーを扱う狭い対象。カンプ画像は目的・情報を補う入力として扱い、理解を実証していない画像モデル連携を既存機能と呼ばない。
- 素材と報告書はローカル保存を基本とする。AI接続を必要とする場合は、利用者が既に利用できる接続を明示的に選び、送る範囲と実行方法を示す。認証情報は通常の作業記録へ保存しない。
- Skill本文、参照、静的教材、将来の検査契約は再利用する。最初から独立した別の規則を実装しない。
- Tauri/Electron等は候補に留める。必要なOS、更新・署名、配布、利用環境、ブラウザ検証手段を実需要で確認してから選ぶ。現時点で技術選定や料金は決定しない。
- 初期導線の評価は「初めての人が素材を選び、意味の選択を説明でき、結果と未検証項目を保存できるか」。インストール成功と実機能の成功を区別する。

## SaaS案

- 妥当な価値候補: チームで意味判断・根拠・差分のレビューを共有し、合意済みのガイダンス版を揃えること。Skillの文書を薄く包むだけなら先に需要を検証する。
- 初期入力は貼付けたHTMLや明示選択したファイルが候補。任意URLの自動巡回・実行を最初から含めない。将来必要ならSSRF、認証ページ、スクリプト実行、容量・保存期間を設計対象にする。
- 共有する入力・AI送信先・保管場所と期間・削除・他の利用者からの分離を確定する。共有リンクや外部AI送信を初期設定で有効にしない。
- 結果状態・意味の対応表・根拠のフォーマットはデスクトップ／Skillと揃える。規則の版、例外、ユーザーが採用した変更を追跡する構想とし、未実装のスキーマや監査エンジンを既存APIとして扱わない。
- 課金方式、契約、アカウント、クラウド運用は未決定。需要検証に先行して導入・課金しない。

## 展開の判断条件

| 段階 | 確認すること | 進む条件 |
|---|---|---|
| Skill改善 | 実際の意味判断・コード例・未検証の境界 | 初めての利用者が例を使って判断理由を説明できる |
| 利用者観察 | 操作のつまずき、CLI/Skillの理解が必要な箇所 | 一貫して現れる課題を観察できる。人数や効果は実施前に捏造しない |
| デスクトップ試作の承認 | 対象OS、ファイル操作、AI接続、成果の保存 | 利用者が範囲・入力・受入条件を選んだ後に実装する |
| SaaS試作の承認 | チーム共有の需要、データ保管・権限・費用 | ローカル入口では解決できない需要と承認範囲がある |

Skillの品質と普及、アプリの使いやすさ、AIの判断精度、HTML/操作の適合性は別々に評価する。GitHubスター数だけで展開判断をしない。
