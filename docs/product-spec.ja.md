# semantic web skill 仕様案

AIが生成・修正するWebサイトの品質を、HTMLの意味、CSSとJavaScriptの基本、アクセシビリティ、実機での表示と操作、検索・AI検索、公開地域の広告・コンテンツ要件まで一貫して扱うスキル集をつくる。

仮称は `semantic-web-skill`。世界の開発者が使い、改善に参加できる公開プロジェクトを目指す。GitHubで1,000スター以上は目標の一つとし、実利用、再利用、継続的な貢献を重視する。スター数、検索順位、AI回答での引用、法令適合を保証するものではない。

作成日は2026年10月9日（日本時間）、技術・提供者方針の資料確認基準日は2026年10月8日。本案は設計仕様であり、リポジトリ、スキル、テストツールの実装完了を示すものではない。以下では、これまでの要望を「必須要件」、具体化のための設計を「構成案」、着手前に選ぶ事項を「未決定事項」として扱う。

## 1 目的と対象

対象は、コーディングエージェントを使う開発者、デザイナー、サイト制作者、コンテンツ担当者。新規サイトの制作と既存サイトの改善の両方に使える設計とする。HTML・CSS・JavaScriptだけのサイトでも利用でき、特定のフレームワーク、CSSライブラリ、AIサービスを必須にしない。

スキルの価値は、見た目の指示を増やすことだけではない。コンテンツに合う構造を選び、動作と表示を検証し、根拠と未確認事項が残る状態で引き渡せることに置く。既存の品質スキルにも測定、アクセシビリティ、SEO、実機確認は存在するため、それらを新規性として主張しない。

公開時に示したい特徴は、次の組み合わせである。

- HTMLの内容モデルと文章・部品の意味から、実装上の判断に落とし込む
- 素のCSSとJavaScriptでも、操作しやすいUIを組み立てる
- 自動テスト、エミュレーション、実機確認を混同せず、証拠を残す
- 検索サービスや広告規制の更新を、出典と適用条件を持つルールとして扱う
- 未対応地域、未実施テスト、判断待ちを隠さず、貢献者が拡張できる

構成の参考は [Web Quality Skills](https://github.com/addyosmani/web-quality-skills)、デザイン品質の参考は [Impeccable](https://github.com/pbakaus/impeccable)、HTMLの専門的な整理は [semantic-html-skill](https://github.com/mikezupper/semantic-html-skill) とする。[Vercel Agent Skills](https://github.com/vercel-labs/agent-skills) と [DESIGN.md](https://github.com/google-labs-code/design.md) も関連プロジェクトとして扱う。設計資料の参照と、各実装の動作検証・性能比較は区別する。

## 2 必須要件

1. HTML Living Standardを基準に、要素の意味、許される親子関係、入れ子、見出し、ランドマークを扱う。
2. FAQ、利用者の声、機能一覧などを、内容に応じて集合・順序・対応関係として構造化する。
3. CSSの基礎を重視し、Tailwindを前提にしない。素のJavaScriptでハンバーガーメニューを正しく実装できる。
4. 操作部品の実際の押せる範囲を、原則として幅・高さとも44 CSS px以上にする。
5. PCでは必要なhover表現を使い、タッチ中心の利用ではhoverに依存しない。
6. 画像の代替テキスト、名前・ラベル、キーボード操作、フォーカス、コントラスト、拡大・リフローを検証する。
7. 最新の端末・OS・ブラウザ情報を調べて対象を選び、画面幅の範囲、境界、回転、ズーム、実機差を確認する。
8. SEO、SXO、AIO、LLMO、GEO、AEOを、根拠のある検索・コンテンツ品質要件に整理する。
9. 広告や訴求は、公開市場、商品区分、媒体、公開日ごとに適用条件を判断する。
10. フッターには著作権表記と、人が使うサイト内ナビゲーションを基本として設ける。
11. 検証結果には実施状況と証拠を残す。未検証の内容を合格・対応済みと表現しない。
12. 英語で利用・貢献できる入口と、日本語の説明を備える。

## 3 構成案と責務

入口となる一つのスキルが依頼内容と対象を整理し、必要な専門スキルだけを読み込む。大きな一枚のプロンプトを毎回読み込む方式は採らない。

専門スキルは次の8分野に分ける。

- `semantic-html`：コンテンツモデル、意味、見出し、リスト、画像、表、フォームの構造
- `css-foundations`：レイアウト、単位、カスケード、文字組み、入力特性、モーション
- `native-interactions`：メニュー、開閉、ダイアログ、フォームなどの状態と操作
- `accessibility`：名前、役割、状態、キーボード、フォーカス、コントラスト、読み上げ
- `responsive-verification`：調査済みの対応環境、幅の範囲、実機差、表示・操作検証
- `search-content`：SEO、検索体験、AI検索、構造化データ、内容と根拠の整合
- `regional-compliance`：適用市場の判定、訴求の根拠、表示・広告ルール、人による判断
- `evidence-reporting`：テストの実行記録、証拠、例外、未解決事項、引き渡し

横断項目の担当は一つに決める。例えば44 CSS pxの基準はアクセシビリティのルールが所有し、CSSとレスポンシブ検証は同じルールIDを参照する。コピーして別々の基準を持たない。

### SKILL.mdの契約

frontmatterは移植しやすい最小構成として `name` と `description` を持たせる。本文には、いつ使うか、必要な入力、作業手順、参照するルール、出力、判断を止める条件を記す。

入口は短く保ち、依頼に関係する参照資料を段階的に読む。インストーラー固有の設定やコマンドは、実際に試したものだけ互換性資料へ記載する。「一般的な構造を採用した」と「各エージェントで導入・動作確認済み」は区別する。

## 4 ルールと証拠のデータ仕様

ルールは安定したIDを持つ機械可読ファイルとして管理する。仕様変更で意味が変わる場合は、改訂履歴と影響するテストを残す。最低限、次の項目を定義する。

- `id`：例 `a11y.target-size.001`。廃止後も別の意味に再利用しない
- `title` と `owner_module`：短い題名と担当分野
- `severity`：影響の大きさ。`critical`、`major`、`minor`、`info`
- `requirement_kind`：標準要件、プロジェクト基準、推奨、任意の好み、法令、行政等の指針、自主規制、媒体ポリシーを区別
- `applicability`：要素、機能、市場、商品分類、媒体、対象期間などの適用条件
- `requirement`：適用された場合に満たす具体的な条件
- `sources`：一次資料URL、該当節、資料の種類、版または更新日
- `effective_from` と `effective_until`：発効期間。確定できないものは不明とする
- `checked_at` と `review_due_at`：最後に根拠を確認した日と次回見直し期限
- `test_method` と `expected_evidence`：静的検査、ブラウザ実行、実機、人の確認など
- `human_review_boundary`：自動判定できない箇所と、必要な確認者の役割
- `exceptions`：適用除外、許される調整、記録すべき根拠

重大度と必須性は別に扱う。例えばブランド上の好みを重大な標準違反として報告しない。施行予定日、公開日、確認日も同じ日付として扱わない。

実行結果の状態は `passed`、`failed`、`untested`、`blocked`、`needs_review`、`not_applicable` の6種類とする。順に合格、不合格、未実施、実施不能、人の判断待ち、適用外を意味する。適用外には理由を必須とし、根拠が足りない場合は適用外へ逃がさない。

結果にはルールID、対象ファイルまたはURL、対象版、実行日時、ツールと版、OS、ブラウザ、端末、画面幅・高さ、DPR、ズーム、入力方式、手順、観測値、期待値、証拠の所在を持たせる。画像、ログ、DOM・アクセシビリティツリー、手動確認記録を用途に応じて結び付ける。

例外承認は、理由、対象、承認者の役割、期限、残るリスクを記録する。不合格そのものを削除して合格に書き換えない。規格の例外に該当する場合と、プロジェクトがリスクを受け入れた場合も分ける。

## 5 HTMLの意味と構造

HTML5という呼称だけで固定せず、HTML Living Standardの内容モデルを参照する。タグを置き換えれば意味が改善するとは限らないため、何の情報で、どう読む・操作するかを先に判断する。

### ページと文章

- `main` は主要内容、`nav` は主要なナビゲーション、`aside` は周辺的な内容に使う
- `article` は独立して扱える内容、`section` は主題を持つまとまりに使う
- レイアウト用の容器には `div` を使える。すべての容器を `section` にしない
- ページを代表する見出しを設け、見出しレベルで内容の階層を表す。文字の大きさのために見出しタグを選ばない
- 「h1は常に一つ」「main直下は必ずsection」のような制作方針と、HTML自体の適合条件を区別する

各要素の許される配置は文脈に依存する。[HTML StandardのSections](https://html.spec.whatwg.org/multipage/sections.html)

### 集合と対応関係

順序に意味がある項目は `ol`、順序を問わない集合は `ul`、名称と説明などの対応関係は `dl` を候補とする。FAQは質問と回答の対応関係として `dl` が適する場合も、質問項目の集合として `ul` と見出し・開閉UIを組み合わせる場合もある。すべてのFAQを一種類に固定しない。

利用者の声を並べる場合は、各証言を一つの項目とするリストが基本候補となる。引用本文には必要に応じて `blockquote` を使い、人物の説明や出典は内容に合う要素で分ける。カードの見た目だけを理由に、全項目を `article` にしない。[HTML StandardのGrouping content](https://html.spec.whatwg.org/multipage/grouping-content.html)

`ul`・`ol`の子に項目を正しく配置する、段落内へ段落以外の大きな構造を押し込まない、リンク・ボタンなどの操作要素を不適切に入れ子にしない、といった内容モデルを検査対象にする。構文検査で通っても、内容との意味的な一致は別に確認する。

### 画像と表とフォーム

各 `img` に `alt` を必須とし、画像の役割に合う代替内容にする。装飾だけの画像は `alt=""` とし、「装飾」という説明を入れない。情報画像、機能画像、複雑な図はそれぞれ情報・操作目的・説明への導線を考える。[WAIの装飾画像ガイド](https://www.w3.org/WAI/tutorials/images/decorative/)

`figure` と `figcaption` は独立した図版等とその説明に必要な場合に使い、全画像へ機械的に付けない。表は表形式のデータに使い、見出しセルとの対応、必要な説明、狭い幅での閲覧方法を設ける。フォームではラベル、入力条件、エラー、修正方法を結び付ける。

フッターの基本構成は、権利者を確認した著作権表記と、主要ページへ移動できるナビゲーションとする。これは本プロジェクトの制作基準であり、全サイト共通の法的義務とは表現しない。人向けのサイトマップと、検索エンジン向けXMLサイトマップは別の役割として扱う。

## 6 CSSとネイティブな操作

### CSSの基準

通常フロー、ボックスモデル、Flexbox、Grid、内在サイズ、オーバーフロー、カスケードと詳細度を扱う。FlexboxとGridは内容に合わせて選び、Grid使用の事前承認を共通要件にはしない。既存プロジェクトでは、その設計や命名規則を尊重する。

文字サイズや余白での相対単位を活用しつつ、すべてをremに固定しない。割合、`min()`・`max()`・`clamp()`、コンテナ基準の寸法、必要なpxを使い分ける。ユーザーの文字サイズ設定、長文、翻訳、フォント未読込でも崩れないことを重視する。

元の単位方針は修正する。メディアクエリ内の相対長は初期値に基づくため、ページに `html { font-size: 62.5%; }` と書いても、メディアクエリの `48rem` を480pxとは扱えない。初期フォントサイズが16pxなら768px相当となる。[Media Queries Level 4の単位](https://www.w3.org/TR/mediaqueries-4/#units)

不必要な `!important` や詳細度の競争は避けるが、カスケードによる上書きや状態差分そのものを禁止しない。低い詳細度、トークン、まとまりのある責務分担を推奨する。`list-style: none` を使う場合は、Safari等でリストの意味が支援技術にどう伝わるかも確認し、必要な場合に `role="list"` を検討する。[MDNのアクセシビリティ上の注意](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/list-style#accessibility)

### hoverとモーション

「PCではhoverを使い、モバイルでは使わない」という要望は、実装上は画面幅だけでなく入力特性に基づいて扱う案とする。`hover: hover` と `pointer: fine` を基本候補にし、タッチ対応PCやマウスをつないだタブレットも検証する。hoverがなくても情報と機能へ到達でき、キーボードのフォーカス表示を別途用意する。

リンク以外へのhoverを一律禁止せず、ボタンなど操作できる対象の反応にも使用できる。装飾的な動きは目的がある場合に絞り、`prefers-reduced-motion` を尊重する。必要な状態変化まで消して操作が分からなくならないようにする。

### ハンバーガーメニュー

CSSの表示切替だけで完成扱いにせず、素のJavaScriptで状態と操作を整える。開閉トリガーは `button`、移動先はリンクを基本とする。見えるラベルを優先し、アイコンのみの場合などに適切なアクセシブルネームを補う。すべてのボタンに機械的な `aria-label` を重ねない。

- 開閉状態を `aria-expanded` と実際の表示に同期する
- 閉じた領域の項目へフォーカスが入らないようにする
- Enter・Spaceによるボタン操作、Tab移動、閉じる操作、フォーカスの戻りを確認する
- 幅変更、画面回転、ページ遷移で状態が破綻しないようにする
- 通常の開閉ナビゲーションと、画面を覆うモーダルを区別する

通常のサイトナビゲーションに、アプリケーション用の `menu` ロールを安易に付けない。モーダル方式を選ぶ場合は、背景操作の抑止、初期フォーカス、モーダル内のフォーカス管理などを別途満たす。[WAIのDisclosure Navigation例](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/) と [Modal Dialogパターン](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

## 7 アクセシビリティの基準

WCAG 2.2 AAを評価の基本目標とする案を置き、プロジェクト独自の基準と区別する。44 CSS pxは独自の操作性基準として、主要なボタン、メニュー、フォーム部品などの実際のヒット領域の幅・高さ双方に適用する。見えているアイコンの大きさだけでは判定しない。

44 CSS pxをWCAG AAの一律要件とは書かない。WCAG 2.2のターゲットサイズは、AAの2.5.8とAAAの2.5.5で基準・例外が異なる。インラインリンクなどは適用条件を分け、例外の理由を残す。[Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)、[Target Size Enhanced](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)

確認対象は、キーボードのみでの利用、論理的なフォーカス順、見えるフォーカス、固定要素による隠れ、名前・役割・状態、色に依存しない説明、文字・部品のコントラスト、エラーの通知、拡大時の閲覧・操作とする。自動検査で検出できない読み上げや操作の理解しやすさは、手動確認として残す。

狭い表示領域と拡大時に、内容や機能を失わず読めることを確認する。二次元の配置が本質的な表・図等には該当する例外があるため、横スクロールを無条件に全禁止するルールにはしない。[WCAGのReflow解説](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## 8 レスポンシブと実環境の検証

### 対応マトリクスの更新

端末名と固定幅のリストを永久に使い続けない。作業開始時とリリース判断時に、対象市場、利用状況、OS・ブラウザの公式情報、利用できる実機を確認してマトリクスを更新する。アクセス解析が利用できなければ、その前提を明示する。

候補にはWindows、macOS、iOS・iPadOS、Androidと主要ブラウザを含めるが、最低対応版は未決定とする。最新版だけに絞るか、旧版をどこまで支えるかは、利用者と保守負担に基づいて決める。調査した日、公式情報のURL、実際に試した版を残す。

各行には端末・OS・ブラウザ、エンジン、版、画面サイズ、DPR、入力方式、実機かエミュレーションか、実施状態を記す。読み上げ確認を行う組合せには、VoiceOver・NVDA等の支援技術とその版も記録する。予定端末が使えない場合は、代替試験と残る確認を分ける。

### 幅の範囲と境界

ブレークポイントは、ナビゲーション、本文、カード、表などの内容が窮屈になる箇所から決める。端末名に合わせて数点のスクリーンショットを撮るだけでは不十分とする。

検証では、対応する最小幅から最大幅までの代表点、各ブレークポイントの直前・境界値・直後の1 CSS px差、縦横回転、ブラウザズーム、文字拡大、長文と翻訳、メニュー開閉などの状態を組み合わせる。境界値は実際に評価されるCSS pxを記録する。コンテナクエリを使う場合は、その容器の幅も同様に扱う。

### 実機差の再現

iPhoneで見える1pxの隙間・線・はみ出しは、DPR、端数計算、変形、境界線、背景、スクロール状態を記録して再現させる。原因を調べず、全体へ `overflow-x: hidden` を加えて隠す修正は避ける。

`100vw` による横はみ出し、スクロールバー、safe area、動的なブラウザUI、ソフトウェアキーボード、固定ヘッダー・フッターも対象にする。OSごとのフォント、代替フォント、字幅、行高、フォーム部品の差による折返しや欠けを確認する。

PlaywrightのWebKitはSafariそのものではなく、端末エミュレーションも実機ではない。結果は「WebKitで確認」「iPhone実機のSafariで確認」のように分ける。[Playwrightの対応ブラウザ](https://playwright.dev/docs/browsers)

画像差分は同じ実行環境を基本に比較し、OSやフォントの違いで生じる差を切り分ける。許容差を増やして不具合を見逃さないよう、更新する基準画像は理由と確認結果を残す。[PlaywrightのVisual Comparisons](https://playwright.dev/docs/test-snapshots)

## 9 検索とコンテンツ品質

用語は入口として残すが、SEO、SXO、AIO、LLMO、GEO、AEOそれぞれに根拠のない独立スコアを作らない。SXOは検索後に目的を達成できる体験として扱い、AIO等の用語は利用する文脈を明示する。

共通の対象は、アクセス・クロール可能性、意味のある本文と見出し、タイトル、適切な内部リンク、正規URL、必要なサイトマップ、画像、表示性能、内容と構造化データの一致である。著者、更新日、根拠、商品の条件は、内容に必要な範囲で正確に示す。存在しない専門性や体験を作らない。

2026年10月8日に確認したGoogle公式案内では、AI OverviewsやAI Modeにも通常のSEOの基本が適用され、特別なschema.orgマークアップは要求されない。Google検索は `llms.txt` を利用せず、検索での表示・順位改善の必須施策とは扱えない。他の利用先に用途がある場合だけ任意に追加する。[Googleの生成AI検索ガイド](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)

FAQは読者に必要なら作るが、リッチリザルト獲得のための必須構成にしない。GoogleのFAQリッチリザルトは2026年5月7日から表示されなくなっている。HowToの提供終了も含め、検索機能の対応状況とSchema.orgの語彙自体の有効性を混同しない。[Google検索ドキュメントの更新履歴](https://developers.google.com/search/updates)

提供者ごとに、クロール、検索への掲載、回答での引用、学習利用、利用者の依頼によるアクセスを分けて確認する。GoogleのSearch generative AI controlは検索内の生成AIへの掲載を扱い、学習利用の制御とは別である。[Search Consoleの公式説明](https://support.google.com/webmasters/answer/16908024)

OpenAIではOAI-SearchBot、GPTBot、ChatGPT-Userの役割を区別する。単一の「AI拒否」スイッチと見なして設定を変更しない。[OpenAIのクローラー説明](https://developers.openai.com/api/docs/bots)

検索提供者のルールには確認日と見直し条件を持たせる。資料を取得できない場合は最後に確認した範囲を示し、最新対応と断定しない。構造化データの存在、長いFAQ、AI向けの言い換えだけを理由に、引用や集客の改善を約束しない。

## 10 地域別の広告とコンテンツ確認

この分野は、適用される条件と確認不足を見えるようにするためのものとする。世界中の法令に適合するという保証、専門家による判断の代替、禁止表現を言い換えれば適法になるという自動判定は提供しない。

### 適用条件

言語だけで地域を決めず、販売・配信する市場、広告主、商品・サービス分類、対象者、媒体、公開予定日を入力とする。同じ英語ページでも米国と英国では確認対象が変わり、複数市場なら複数のパックを評価する。非商用の技術文書など、該当しない項目は理由を付けて適用外にできる。

情報が不足し、公開判断に影響する場合に限って必要事項を尋ねる。すべてのページへ薬機法の確認や法務承認を一律要求しない。一方、対象市場や商品区分が不明な広告を、推測だけで適合済みにしない。

### 地域パックの構成案

- 日本：景品表示法の表示規制を起点に、商品分類に応じて薬機法関連などを追加する。[消費者庁](https://www.caa.go.jp/policies/policy/representation/fair_labeling/representation_regulation)、[厚生労働省](https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/kenkou_iryou/iyakuhin/koukokukisei/index.html)
- 米国：体験談・推薦・重要な関係の開示など、FTCの指針と対象となる規則を区別して扱う。[FTCのEndorsement Guides解説](https://www.ftc.gov/business-guidance/resources/ftcs-endorsement-guides-what-people-are-asking)
- EU：食品の健康強調表示など、分野に応じた規則と許可された主張・使用条件を確認する。EU域内の個別国の要件も別途確認する。[欧州委員会の登録情報](https://food.ec.europa.eu/food-safety/labelling-and-nutrition/nutrition-and-health-claims/eu-register-health-claims_en)
- 英国：CAP Code等の広告自主規制と法令を区別して記録する。[ASAとCAPの説明](https://www.asa.org.uk/type/non_broadcast/code_folder/preface.html)

上記は調査・実装候補であり、4地域の全業種対応を意味しない。最初の対応パックは、対象範囲と出典、適用条件、試験事例、人の確認範囲が揃ったものだけを公開する。媒体独自の広告ポリシーも法令とは別のレイヤーにする。

### 主張と根拠

効果、価格、比較、最上級、数値、体験談、保証などの主張にIDを付け、原文、根拠資料、対象商品、試験条件、対象期間、対象者、制限、掲載場所を結び付ける。「当社調べ」や「個人差があります」を付けるだけで合格にしない。根拠が本文の主張を実際に支えるか確認する。

必要な開示は、原稿内に文字があるだけで完了としない。最終レンダリングで、主張との距離、文字サイズ、コントラスト、折りたたみ、モバイルでの隠れ、表示タイミングを確認する。画像内文字、代替テキスト、メタ情報、構造化データも本文と矛盾しないか見る。

根拠不足や解釈が必要なものは `needs_review` とし、担当者が判断できるよう該当箇所、理由、根拠、修正候補を渡す。対応していない市場は未対応として示す。リスクの高い主張を削除・限定した場合も、残る全体の印象を再確認する。

## 11 実行手順と出力

次の二つの利用モードを提案する。

- 新規生成：目的、対象読者、情報、ブランド、技術条件、公開市場を整理し、構造・実装・検証を進める
- 既存レビュー：現在のコードと表示・操作を確認し、指摘と根拠をまとめる。修正まで行うかは依頼範囲に従う

共通の手順は、入力と適用範囲の確定、必要なルールの選択、一次資料の確認、内容と構造の設計、生成またはレビュー、静的検査、ブラウザ検査、実機・手動確認、残課題の整理、引き渡しとする。小さな作業で毎回大規模な調査を強制せず、判断に必要な範囲へ絞る。

引き渡す内容は、対象と変更の要約、適用ルールの版、使用環境、実施した検査、結果と証拠、未実施・実施不能・判断待ち、例外、次の作業とする。必要に応じて `review.md`、`test-results.json`、`test-matrix.json`、`claim-evidence.json` と証拠フォルダーへ出力する案とする。

レビュー依頼は修正や公開の許可にはならない。スキルを読み込んだことを、監視の開始、購入、認証情報の取得・保存、ブラウザの許可や規約の承諾、外部送信、デプロイの許可として扱わない。実行環境の権限と、その作業に対する利用者の指示を守る。

## 12 検証ツールと完了条件

導入候補はNu Html Checker、axe-core、Playwright、Lighthouse、必要に応じたCSS・JavaScriptの静的検査とする。ツールの導入、コマンド、CI設定、対応版は実装時に検証する。現段階で、これらがプロジェクトで動作済みとはしない。

自動検査だけでアクセシビリティ全体、意味の適切さ、法令適合を合格にしない。スクリーンショットは表示、DOMは構造、操作記録は動作というように、証拠が支える範囲を限定する。

Core Web VitalsはLCP 2.5秒以下、INP 200ミリ秒以下、CLS 0.1以下を良好域の参考とする。フィールド評価の75パーセンタイルと、特定環境でのラボ計測を区別する。実利用データがないサイトに実測INPやフィールド合格を作らない。[Web Vitalsの公式説明](https://web.dev/articles/vitals)

作業完了の条件は、依頼範囲の実装またはレビューが揃い、適用ルールの結果が記録され、重大な未解決事項と残る確認が明示されていることとする。「報告が完成した」と「公開してよい品質が確認できた」は分けて判断する。

適用対象の必須項目に `failed`、`untested`、`blocked`、`needs_review` が残る限り、「検証完了」「公開準備完了」「全項目合格」と表示しない。例外承認の記録だけでこの判定を通過させず、ルールが定める適用除外や代替条件が成立したかを再評価する。確認できない項目が残っていても、状態と必要な対応を記した報告書自体は完成できる。

## 13 比較デモと評価設計

見た目が近い二つのページを用意し、構造と操作の違いを確認するデモを作る。FAQ、利用者の声、ナビゲーション、フォームを含め、コード、画面、アクセシビリティツリー、キーボード操作を対照できる構成とする。

画像類似度やSSIMは見た目の近さの補助指標に限る。高い類似度を意味構造・アクセシビリティの改善証明にはしない。比較のためだけに現実離れした悪いコードを作り、容易な勝利を示す評価も避ける。

生成品質の評価では、同じ依頼、入力素材、モデル、設定、時間・トークン予算を使い、スキルなし、適切な一般的基準、関連スキルなどと比較する案とする。既知の例題と未見の課題を分け、HTML不適合、操作失敗、重大なアクセシビリティ問題、表示崩れ、根拠のない合格判定、作業コストを評価する。

改善率は実施後の結果からのみ報告する。公開するのは、権利と公開範囲を確認した試験用素材、手順、環境、集計結果とする。利用者の非公開コード、認証情報、個人情報、顧客素材をテスト証拠として自動公開しない。

## 14 元の制作方針の扱い

コンテンツの意味、根拠の確認、段階的な検証、比較デモ、引き渡し資料という考え方は引き継ぐ。矛盾や過度な一般化を含む指定は、今回の共通基準へ修正する。

任意プロファイルへ移すものは、左右非対称の必須化、装飾数、影・カード・グラデーションの制限、特定フォント、固定文字数、二重ラッパー、独自の命名方式、AIDCA・Sugarmanを使う日本語LPの編集手順とする。これらは、対象のブランドやコンテンツに適した場合に選ぶ。

共通ルールから外すものは、Gridの承認必須、CSS再定義の全面禁止、全寸法rem固定、リンク以外hover禁止、全画像のfigure化、FAQ・HowTo・llms.txtの無条件必須化である。短い回答を文字数だけで引き延ばさず、必要な情報と根拠で長さを決める。編集フレームワークの採用を、法令確認の代わりにしない。

## 15 実装段階と公開条件

段階は実装順を示す。後半に置いた要件も全体の対象から外さない。

1. 仕様と土台：名称、ライセンス、ルール分類、結果スキーマ、英日README、貢献方法、初期対応範囲を確定する。
2. 基本品質：HTML、CSS、ネイティブ操作、アクセシビリティ、レスポンシブのルールと小さな実例を実装する。検索・地域対応も入口と未対応判定を備える。
3. 証拠と更新：自動検査、実機記録、比較デモ、検索提供者の確認、検証済み地域パックを追加する。
4. 公開と改善：互換性を実測し、未見の課題で評価し、公開可能な結果と既知の制限を出す。利用者の報告を回帰テストに変える。

最初の公開版でも、必須要件の各項目がどのルール・資料・テストで扱われるか追跡できることを条件とする。未実装部分はロードマップに明示し、未対応を合格として返さない。

貢献は、不具合再現、ブラウザ差、適用条件の修正、一次資料の更新、翻訳、事例の追加から受け付ける。ルール追加には、出典、適用範囲、合格・不合格・境界の事例、誤検出の検討、人が判断すべき範囲を求める。ルールの意味を変える変更は、版と移行の説明を残す。
