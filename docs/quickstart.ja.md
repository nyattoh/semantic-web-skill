# クイックスタート：リポジトリを設計資料として使う

[English](quickstart.en.md) · [現在の実装状況](starter-status.md) · [静的比較例](../examples/semantic-comparison/README.md)

9つのスキル草案と3経路を人が試すための案内です。検証済みのインストール手順ではありません。リポジトリ全体をローカルのコンテキストとしてエージェントから参照できる状態にし、相対パスを保ちます。ルートから `skills/semantic-web/SKILL.md` を入口に指定してください。単一ファイルだけのコピーでは参照先が失われます。特定ホストでの発見・呼出し・実動作は検証していません。

## 1. 経路と成果を選び、入力を添える

必要な成果に応じて1経路を選びます。両方の成果が必要な場合だけ経路をつなぎます。

- **comp-to-html**：カンプまたは読み取れる書き出し、実際の文章・素材、既知の移動先・操作、技術条件を渡し、実装か計画かを指定します。画像だけではコード品質、DOM順序、リンク先、フォーム動作は分かりません。
- **brief-to-comp**：目的、利用者、コンテンツ、ブランド、操作を渡し、カンプだけか、カンプとHTMLかを指定します。利用可能で許可されたデザイン環境がなければ、設計仕様と明示した代替成果（範囲内で可能ならローカルHTMLプレビュー）を使います。代替成果はネイティブなデザインファイルではありません。
- **review**：既存ソースと版、ページまたはURL、観察内容、レビュー範囲を渡し、指摘を求めます。修正は修正依頼を含む場合だけ行います。ソースしか確認できない場合、表示・操作の検査は残ります。

変更してよい範囲、保存先、技術条件、使えるツール、言語、必要なら対象市場を添えます。既知の情報を再質問せず、意味・必要な操作・範囲を左右する不足だけ確認します。フォーム送信先が不明なら未決事項として残し、バックエンド、検証応答、送信成功を作りません。

## 2. 最小限の資料を選ぶ

[入口スキル](../skills/semantic-web/SKILL.md)と[共通フロー](../skills/semantic-web/references/workflow.md)から始めます。選んだ経路の[カンプからHTML](../skills/semantic-web/references/comp-to-html.md)または[ブリーフからカンプ](../skills/semantic-web/references/brief-to-comp.md)を読みます。レビュー手順は共通フローにあります。毎回すべての文書を読む必要はありません。

意味の設計と要素選択には [semantic-html](../skills/semantic-html/SKILL.md) を使い、対象領域に必要な content-model/pattern の参照先を読みます。操作・フォームなら [native-interactions](../skills/native-interactions/SKILL.md)、レイアウトなら [CSS](../skills/css-foundations/SKILL.md)、該当する検査には[アクセシビリティ](../skills/accessibility/SKILL.md)、幅や入力の変化には[レスポンシブ検証](../skills/responsive-verification/SKILL.md)を加えます。検索・地域の草案は関連するときだけ読みます。実際の結果を渡す際は[証拠の報告](../skills/evidence-reporting/SKILL.md)と [handover](handover.md) を参照します。これらは読む指示資料であり、読込みによって検査が実行されるわけではありません。

## 3. このプロンプトをコピーして使う

最初の3行を埋め、リポジトリをコンテキストに保ち、その環境へ共有してよい入力だけ添えます。外部アップロード、課金、インストールを意味するものではありません。

```text
経路: <comp-to-html | brief-to-comp | review>
入力と成果: <カンプ/ブリーフ/ソース、文章、移動先/操作、条件、必要なら市場; 計画/カンプ/HTML/指摘>
許可する変更と保存先: <対象ファイル、出力先; 修正依頼がなければレビューのみ>
リポジトリ全体をローカルのコンテキストとして使い、skills/semantic-web/SKILL.md から始めてください。9つのスキルは草案として扱い、共通フロー、選んだ経路、最小限の関連スキルと参照資料を読んでください。
最初に semantic blueprint を提示してください：コンテンツの事実/出典、まとまりと読順、見出し、要素と理由、移動と操作の区別、ラベル/状態、レスポンシブの意図、未決事項。その後、依頼されたマークアップ、カンプ/明示した代替成果、またはレビュー指摘を範囲内で作ってください。不明な移動先やフォーム送信先は未決のまま残し、サービスを作らないでください。
環境で利用できる許可済みの検査を実行し、要件、対象/版、方法/環境/日時、期待/観測結果、証拠の保存先を passed, failed, untested, blocked, needs_review, not_applicable のいずれかで報告してください。資料の読込みや画像を見ることは検証ではありません。成果物のパスと残る判断を人の指示による調整のために渡し、草案からホスト対応、アクセシビリティ適合、法令適合を断定しないでください。
```

## 4. 成果と証拠を確認する

受け取る順序は **semantic blueprint → マークアップ/デザインまたは指摘 → 実際の検査と証拠** です。ブリーフ経路でも設計の前に blueprint を作り、HTMLへ進むのは依頼された場合だけです。[静的比較例](../examples/semantic-comparison/README.md)で「コンテンツの事実 → 要素 → 操作 → 検査」の対応を確認できます。外観の一致からコード品質は分かりません。ソースを比較したうえで、該当する実動作を別途検査します。

根拠も分けます。`standard` は規格由来（義務・推奨・記述の強さも記録）、`convention` は案件の方針、`judgment` は内容の解釈です。方針に合わないだけでHTML規格違反と扱いません。

要件・検査ごとに状態を1つ付けます。

| 状態 | 意味 |
|---|---|
| `passed` | 実際に検査し、記録した証拠が指定の要件を満たした。 |
| `failed` | 実際の観測が要件を満たさない。再現手順と影響を残す。 |
| `untested` | 検査を実施していない。残る作業を示す。 |
| `blocked` | 必要な入力・権限・出典・環境がない。依存条件を示す。 |
| `needs_review` | 解釈または人の判断が残る。確認担当と論点を示す。 |
| `not_applicable` | 条件が該当しない。理由を示す。証拠不足の代用にはしない。 |

例：対象 `fixed.html`、要件「Clear note は送信しないボタン」、方法「Python HTMLParser による fixture assertion」、期待/観測 `button type="button"`、状態 `passed`、証拠はローカルの検査出力、加えて実行日時とPython/OSの版を記録します。合格するのはこの静的 assertion だけです。キーボード起動やフォーカスは実際に操作するまで `untested` です。送信先不明の問い合わせは `blocked` とし、成功を模擬して解決扱いにしません。法令・提供元ポリシーの解釈は助言として `needs_review` にします。

パス、証拠、未決事項を渡し、人が調整箇所を指示できるようにします。報告が完了しても製品動作が未検証なら、公開準備完了としません。

## 5. ローカルの静的例を試す

[bad / fixed / boundary の説明](../examples/semantic-comparison/README.md)とソースを読み、必要ならHTMLファイルをローカルで開きます。ビルド、依存関係のダウンロード、インストーラーは不要です。この開き方はブラウザー対応の保証ではありません。限定した文書・fixture 検査の再現コマンドと確認環境は[テスト案内](../tests/README.md)にあります。

これらの検査は汎用HTML監査、WCAG評価、エージェント検証ではありません。実動作デモ、エンジン/インストーラー、ホスト動作、適合性、支援技術、実機、地域パックは未検証です。詳しい境界は[実装状況](starter-status.md)を確認してください。
